# Translation

**Translate this item’s transcription(s)** turns a finished Arabic transcription into an English translation, one page per page, using the same Gemini pipeline. It assumes a Zotero literature note in the format created by **[ScholarWeft](https://community.obsidian.md/plugins/scholar-weft)**, which is recommended as a companion plugin for Midad Arabic Sources.

Run it from a `@citekey` note, preferably generated by ScholarWeft. As with transcription, the item route assumes the `@citekey` literature note in the folder set under **Transcription and translation → Literature notes folder** (blank uses ScholarWeft’s `literatureNoteFolder`, then a vault-wide search by note name); without one, translate a transcription from its own note, or use the standalone transcription workflow first. A dialog lists that item’s transcriptions (all checked by default) plus any PDFs it found; deselect the ones you do not want, optionally set a **Volume** number, and click **Translate**.

- The translation is submitted as a Gemini batch job and written to `<Sources>/Translations/` as `@<citekey> - translation.md` (or `… - translation - vol. N.md`) when it belongs to a Zotero item. A standalone PDF route, with no Zotero citekey, uses `mas-<slug> - translation.md`. Translations are automatically made annotatable, with all volumes of a series sharing one annotation note.
- A translation mirrors its transcription note’s aliases and is linked from it, so the two sit side by side.
- The batch is archived under `.midad-arabic-sources/archive/`, so it can be reprocessed later.
- **One page per request**, as transcription is one page per image. A page is cut at its `#### p. N` heading, and a page's own headings (`## Lesson Thirty-Two`, `### Sūrat Maryam`) are content, not boundaries. Two pages in one context let the model attach one page's apparatus to the other — its footnotes were several times written at the end of the *next* page's section, where the page structure then placed them, although the source had them on the earlier page. One page cannot be misattributed that way. If a response comes back without its page heading, the request's own heading is restored from it, so a page cannot vanish from the note.
- The same progress panel and log apply as for [transcription](./transcription.md).

## Post-processing

A translation is normalised on the same funnel as a transcription, with a few rules of its own.

- **Footnotes are the ordinary kind.** Gemini sometimes writes both callouts on one page — an empty `footnotes` and the content in `arabic-footnotes`, which a stylesheet sets right-to-left. A translation is not an Arabic note, so the Arabic callout is renamed, adjacent footnote callouts are merged into one, repeated items are dropped, and the result is a single `>[!footnotes]` per page. The label the model writes for the list is never prose and never survives: `Footnotes:`, `> Footnotes:`, `>Footnotes:`, `**Footnotes**`, `**Arabic Footnotes**` and a `### Footnotes` heading are all the same label — on every page of this corpus that carries a heading there, the source page has none, because page footnotes are the page's apparatus rather than a titled division (a book with endnotes names them, and prints a list under the name). The label becomes the callout header, or is dropped when the callout already has one, and definitions the model wrote as ordinary numbered paragraphs (`<sup>1</sup> …`, `¹ …`) or wrapped in literal tags (`<arabic-footnotes> … </arabic-footnotes>`) are folded into it as `> - 1 – …`. A page whose list never became a callout at all — a bare blockquote of `>1 – …` items with no header and no label — is recovered from the page's own `<sup>` anchors, and only when the item numbers match those anchors exactly. The model frequently omits those anchors in the body, so a numbered list that **ends the page** is the page's footnotes too: it must start at 1, have no gaps in its numbering, and sit with nothing after it but the page rule. A missing anchor is fine — the list may cover more verses than the body marks — but an anchor the list does not account for refuses the conversion, and the same list in the middle of a page is a quotation and stays one. Two shapes the model also writes are read the same way: items numbered with a period and no dash (`>1. Aḥmad transmitted…`), and a list that restarts at 1 because a page's notes and its translator's were merged into one blockquote. A rule that introduces a run of number-led paragraphs — `---`, `***`, `___`, or a bare `<br>` — is the model's footnote section rather than a page break — pages are delimited by their `#### p. N` headings, and a rule inside one is that section's edge — so the rule goes and the paragraphs become the callout's items: a line beginning with a footnote number is the footnote section, wherever the count starts (a page whose notes continue the previous page's is written `⁴ ⁵ ⁶`). An item written without its bullet becomes the conventional `> - 1 – …`. A definition's number is read in every form the model uses — `<sup>1</sup>`, `^(1)^`, `^(1)`, `1`, `¹`, `١`, with or without a dash after it — and the markdown footnote is read too: `[^1]: …` and a named `[^talhah-bio]: …` become items (named ones numbered in the order they are defined), while every `[^…]` anchor in the body becomes a `<sup>N</sup>` reference, because a callout item is not a footnote Obsidian can link to. A number followed by a **dash** (`1 - …`, `^(3)^ – …`) is a definition wherever it stands; a number followed by a **period** (`1. …`) is a body list and stays one; a footnote number is read in any of the three numeral forms — `1`, `¹` and `١` — both as an item's number and as the reference printed in the page's text. A block that ended up on the wrong page is put back: translation is requested two pages at a time, so a mislaid block can only be one page late, and it is moved one page back when the page above refers to its numbers in its own text and has no footnote block of its own. Anything less clear-cut — a page that refers to the numbers itself, a page above that already has its notes, a block two pages away — is left exactly where the model put it.
- **Backticks are quotes.** The model marks a term — or a whole couplet — with backticks, and Markdown then sets it in code type. The vault quotes with the single curly pair, so `` `x` `` becomes ‘x’. A fenced code block is left alone.
- **Citations are canonical links.** The model has learned the vault’s older sūra note names and writes them itself — `([[004 An-Nisa#29|al-Nisāʾ: 29]])` — which is an unresolved link carrying the model’s own display text. The citation is rewritten to `[[Q004#29]]`, so the plugin paints it in the note’s language like any other. A parenthesised verse number left after a link, a `۞` divider inside a gilded quotation, and stray emphasis inside the marks are removed as well.
- **A verse is cited once per run.** A translated tafsīr glosses a verse word by word, and every gloss used to carry its own link. Consecutive quotations of the same verse within one paragraph now keep the citation on the first and the last only — the rule the Arabic commentary already follows — so the reader is told once where the passage is and once where it ends. The margin's `|:` marker is not a citation and is left alone, and a blank line ends the run, so a verse quoted again a page later still carries its link.
- **A citation reads in the language of the note, or of its paragraph.** A translation is an English document even when it carries no property saying so — see [Qur’ān citations in source text](./templates.md#qurān-citations-in-source-text).

These are not prompt behaviour: they run locally after the model, so a re-render of a saved batch applies them to the existing output.

## Prompts

The dialog has the same **Prompt** controls as transcription: a dropdown beside **Select all** / **Select none**, with **Modify selected**, **Create a new prompt from selected**, and **Delete selected prompt**. Prompts live in `.midad-arabic-sources/translation-prompts.json`, and the selected prompt is sent as the batch job's system instruction. **Default prompt** can be edited but not deleted.

The editor holds only the **text-specific** part. The pipeline appends it to the shared, hardcoded format contract (page headings, `---` separators, blank lines, no hard wrapping) and the general translation rules (structure, poetry, footnotes, italics and quotes). The default text-specific part names the source language, the target language, Qur'an-quote formatting, and IJMES transliteration.

There is no separate “re-translate selected pages” command yet; re-running **Translate this item’s transcription(s)** on a transcription replaces its translation. Page-level re-translation is on the roadmap.

Translation needs the same prerequisites as transcription: a **Gemini configuration assigned to translation** on the LLM settings page, and Python 3 with `google-genai`, `requests`, and `pymupdf` — see [Dependencies](./dependencies.md).
